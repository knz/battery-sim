What replaces it is the pane's "N changed from default" count, which is what §2′.6 asks a collapsed pane to say. ## The six rules in here that are easy to break **The root keeps `id="panel-params"` and the form keeps `id="params-form"`.** Both are contracts: `POST /w/{id}/params` returns THIS template rendered standalone and the browser swaps the root's outerHTML (the delegated handler in workspace_results.html), while the form id is what that handler and the cost toggle's `requestSubmit` resolve. **The advanced pane is a `
`, never a conditional.** Collapsing is a DISPLAY state and must not be a reset (§2′.6, and §2′.4 before it): a `
` keeps its contents in the DOM and in the submitted form body, whereas rendering them only when open would submit a collapsed pane as a screenful of cleared fields and silently wipe every setting behind it. The tabs are CSS-driven for the same reason — see below. **The tabs are radio inputs plus CSS, and every tab's panel is in the DOM at all times.** A JS-swapped or conditionally-rendered tab would submit the two tabs the user did not open as cleared fields, which is the same defect as a conditional pane. The three radios are `name="params-tab"` and carry NO dotted path, so `parse_form` never sees them; `.tab-panel` is hidden by CSS from the checked radio's `:checked` state (app.tailwind.css), which keeps the inputs submittable — `display:none` does not exclude a control from a form body, only `disabled` does. **Charge and discharge share the third tab, with the overlap warning below both.** §2′.6 requires it: the warning compares band A/B against band C/D, so splitting them would put the warning on one tab and the values it indicts on the other. The warning is therefore rendered AFTER both cards rather than inside the discharge one, which is where §2.3 had it. **The `sections` marker names exactly the controls this render drew.** `params_view._section` gates every checkbox on it and an over-claiming marker CLEARS the stored value of a checkbox the screen never rendered — phase 3 shipped two such defects. This template draws every control `params_view._sections_for` enumerates, INCLUDING `setup.simulate_cost` (the cost toggle, which §2′.7 moved out of the setup band into the results block below). It does NOT draw `setup.has_pv`; see `_sections_for`'s docstring for why the `setup` marker is still safe, and `results_screen_view` for what moved where. **The cost toggle is NOT in this file.** §2′.6 puts it "inside the results block, under the period selector and above the result sections — not in the battery box". It lives in `_panel_results.html` and carries `form="params-form"` (HTML's explicit form association), the same mechanism `_setup_band.html` used before it was deleted. That is why this form's `sections` claims `setup` even though the control is drawn a panel away: one form, one POST, one validation, one swap. The view-model is app/params_view.py, unchanged. Field entries are dicts: `.name` (the dotted path), `.value` (a formatted number, or the raw string the user typed), `.errors` / `.warnings` (already-English messages the template translates via `_()`), `.invalid`. `view.advanced_changed` is `results_screen_view.advanced_changed_count` — how many pane values differ from appendix A.
