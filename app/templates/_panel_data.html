{# _panel_data.html — Panel ① Data input, slot-first (specs/02-ux-wireframes.md §2.2, §2.1). Collapsed to a one-line summary; expands to the slot-first body: a short intro, the slot roster, and the data-quality box. The values are either the static sample (app/sample_data.py `data`) or a real persisted dataset's view-model (app/data_view.py `panel_data_from`) — the two share this shape. Slot-first design: the panel leads with the roster of data slots (roles + requirement markers). Each slot ROW shows its chosen source (row.source) or a "Choose source…" affordance; clicking the affordance opens the shared right-side source-picker DRAWER (mounted in index.html), which lists that slot's available sources (row.sources) and their config. The drawer is opened by JS reading data-* attributes off the row's button (ha_fetch.js). The Home Assistant entity (statistic id) for a slot is chosen INSIDE the drawer, not on this main row: there is no entity to choose for any source other than Home Assistant. The row's source button therefore also carries the chosen HA entity inline in its label (e.g. "Home Assistant · sensor.…import_t1"); ha_fetch.js updates that label after the user picks an entity in the drawer this session (the persisted view-model does not carry a re-selectable statistic id, only a "(res, N intervals)" coverage summary, so a persisted HA slot shows just the source label until re-picked). The roster table has three columns: Role, Req, Source. The Home Assistant CONNECTION is SHARED and lives in a MODAL (#ha-config-dialog in index.html), opened by a "Configure" button beside the Home Assistant radio in the drawer — not a panel-level card. The user tests/connects once (URL + token + Test connection); every HA-source slot then reuses that connection — the drawer's single entity
