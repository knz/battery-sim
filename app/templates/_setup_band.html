{# _setup_band.html — the setup band (specs/02-ux-wireframes.md §2.1 "The setup band"). Holds `simulate_cost` — *simulate cost savings?* — the one scope choice that shapes MORE than the data step: it decides which boxes panel ② shows (§2.3) and which sections panel ③ renders (§2.4), so it does not belong to any single panel. It is a REAL control now, no longer pending: the cost path is built, so the radios POST and the answer takes effect. `simulate_cost` is retired in app/features.py rather than deleted, so its interest counter keeps its meaning. **How it posts, and why it has no form of its own.** The two radios carry `form="params-form"` — HTML's explicit form association — so they submit with panel ②'s form even though they sit above it in the document. That is deliberate: the answer changes which boxes panel ② draws, so the response has to be the re-rendered panel, and one form means one POST, one validation and one swap. A separate form here would either need its own fetch/swap path or would post WITHOUT panel ②'s fields, which `parse_form` would treat as "inherit everything" — correct, but it would silently discard whatever the user had typed into the panel and not yet submitted. index.html's delegated `change` handler on `#setup-band` requests the submit; the panel's existing submit listener does the rest. `sections` (rendered by _panel_params.html) carries the `setup` marker that tells `parse_form` this submission really drew the band — a radio group's absence is otherwise indistinguishable from a partial POST. The two DATA-shaping answers that used to live here — `has_pv` and `has_battery` — now sit at the top of panel ① (_panel_data.html, "Scope questions"). Both exist to decide which SLOTS that panel asks for, and they are committed by its fetch button, so the answer belongs next to the roster it governs rather than in a band above it. It is a scope selector, not a stepper panel: always visible, never collapses, no CTA, not numbered. UI chrome is wrapped in _() for translation (English/Dutch). #}
