{# _data_roster.html — the slot roster (specs/02-ux-wireframes.md §2.2 slot-first, specs/20-workspaces-ux.md §2′.5). Shared by panel ① (_panel_data.html) and the configure-data screen (workspace_data.html): ONE copy of the roster markup, because every id and data-* attribute below is a contract with app/static/ha_fetch.js and two copies would be two things to keep in step with it. Slot-first design: the table leads with the roster of data slots (roles + requirement markers). Each slot ROW shows its chosen source (row.source) or a "Choose source…" affordance; clicking the affordance opens the shared right-side source-picker DRAWER (mounted by whichever page includes this — index.html or workspace_data.html), which lists that slot's available sources (row.sources) and their config. The drawer is opened by JS reading data-* attributes off the row's button (ha_fetch.js). The Home Assistant entity (statistic id) for a slot is chosen INSIDE the drawer, not on this row: there is no entity to choose for any source other than Home Assistant. The row's source button therefore also carries the chosen HA entity inline in its label (e.g. "Home Assistant · sensor.…import_t1"); ha_fetch.js updates that label after the user picks an entity in the drawer this session (the persisted view-model does not carry a re-selectable statistic id, only a "(res, N intervals)" coverage summary, so a persisted HA slot shows just the source label until re-picked). The table has three columns: Role, Req, Source. **`#slot-roster` is the module gate.** ha_fetch.js returns immediately when this node is absent, which is what makes the whole file inert on a page with no roster and fully functional on any page that includes this partial. It also carries `data-ingest-ws`, the whole workspace-scoped ingest path, rendered server-side so ha_fetch.js never has to know the URL layout. The roster is gated by all three scope answers (§2.2, §2.1): the solar row shows only when cfg.has_pv, the two existing-battery rows only when cfg.has_battery, and the two Spot price (min/max) rows only when cfg.simulate_cost. Gated rows are RENDERED and carry `hidden`, so the radios can re-gate the table client-side without a round-trip (ha_fetch.js `applySetupGating`). The server computes the initial hidden state, so the first paint is right with JS off. A hidden row is not fetchable: ha_fetch.js skips hidden rows when collecting the slots to stream. The `req` → marker mapping: required ●, conditional ◐ (PV-only), cost_optional ◒ (cost-simulation-only), optional ○. A row whose view-model carries an `info` blurb (SlotSpec.info, specs §4.1) also renders an ⓘ button next to its role label; clicking opens the shared #slot-info-dialog (filled by ha_fetch.js from the button's data-info-title/body). Rows without `info` render no icon, so the affordance is generic — a new series gets one by populating that field, not by editing here.
