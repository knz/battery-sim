# CI failure: app/static/app.css out of date on `worktree-ux-features`

> **Note on this file's wording.** Tailwind scans repository files for class names, and
> this directory is inside the scan. Writing the offending utility class verbatim here
> would make Tailwind emit a rule for it and break the very CI gate this file documents —
> which is exactly what happened during the work below. The class is therefore written
> throughout as `whitespace-` + `nowrap`, never as one token. Do not "fix" that.

## Task Specification

PR #8 (https://github.com/knz/battery-sim/pull/8) has a failing CI check: the
`css-freshness` job ("app.css is up to date") in `.github/workflows/test.yml`.

The user's instruction: resolve the divergence by **amending the commit that introduced
it**, rather than appending a fix-up commit on top. The branch carries seven commits, so
the offending one had to be identified first.

## Investigation

`app/static/app.css` is generated by `npm run build:css` (Tailwind v4 + daisyUI v5) from
`app/static/src/app.tailwind.css` plus the class names used in the templates, and the
generated file is committed. CI regenerates it and fails on any diff.

The generated file is a single minified line, so `git diff` reports only "line 1 changed"
and is unreadable. Comparing committed vs. rebuilt output character by character located
the difference precisely: the rebuild inserts exactly one rule, `whitespace-` + `nowrap`
(169144 → 169182 bytes), and removes nothing.

`git log -S` attributes that class to commit **e10d6d0** "Derive the results screen's
opening period and flag short series", which added it at
`app/templates/_panel_interval.html:201` without regenerating the CSS. Checking out
e10d6d0 detached and rebuilding reproduced the one-rule insertion, confirming it as the
origin. `master` is clean.

## Obstacles and Solutions

Three wrong turns, worth recording because the first two produced confident-looking but
false measurements.

1. **A per-commit script that did not isolate commits.** The first attempt checked out
   only selected paths over the working tree between iterations, so each build saw a
   mixture of that commit's files and leftovers from others. It reported DRIFT at all
   seven commits. Fixed by checking out each commit into a **detached HEAD**, so the
   whole tree matches the commit under test — the same condition CI runs under.

2. **The first rebase folded the CSS into the wrong commit.** A `git rebase --exec`
   running the rebuild at each step amended the fix into the branch's *first* commit,
   whose templates do not contain the class at all. Detected by inspecting the amended
   commit rather than trusting the rebase's success message. Reverted via a backup
   branch and redone as an explicit amend of e10d6d0 followed by `git rebase --onto` to
   replay the four later commits.

3. **This changelog file itself broke the check.** After the amend, verification still
   showed drift at the two commits *preceding* e10d6d0 — commits whose templates lack
   the class. The cause: Tailwind v4 auto-detects sources across the project on top of
   the explicit `@source '../../templates'`, so this file, which quotes the class name
   while explaining the bug, caused a rule to be generated for it. Confirmed by moving
   the file out of the tree and re-running: all seven commits clean. Hence the wording
   note at the top.

   This is a standing hazard, not a one-off: **any** committed file that mentions a
   Tailwind class name as a bare token can alter the generated CSS. Prose about CSS in
   this repository must avoid writing class names as single tokens.

## High-Level Decisions

- Fixed by amending e10d6d0 to carry its own regenerated `app.css`, per the user's
  instruction. The alternative — one "regenerate CSS" commit at branch tip — was not
  taken; it would leave the intermediate commits individually failing the freshness gate.
- The regenerated file comes verbatim from `npm run build:css` against the versions
  pinned in `package.json`, so CI's rebuild should reproduce it byte for byte.
- The branch was rewritten, so PR #8 needs a force-push.

With this changelog present in the tree, every commit on the branch was checked out

it now passes at each commit rather than only at the tip.

once the force-push is confirmed good.
