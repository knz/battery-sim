# CI setup — tests on PRs, image builds on tagged releases

## Task specification

Set up GitHub Actions CI for the project:

- **run the test suites on all pull requests**;
- **run the image builds on tagged releases**.

Assume GitHub. The repository is `github.com/knz/battery-sim` (not yet public).

This is phase 6 of `20260805-desktop-packaging.md`, widened: the original phase 6 covered only
the release-build matrix, and this task adds PR test CI in front of it.

## The measurement that reframed the design

`U6` in `20260805-desktop-decisions.md` records a standing instruction not to run the full pytest
suite during development because "it contains benchmarks and is slow", with an open question about
whether a marker exists to separate them out.

Measured on this machine before designing anything, because the whole shape of PR CI depends on
it:

| selection | wall clock | tests |
|---|---|---|
| `tests/test_benchmark.py` | **15s** | 45 |
| `tests/test_smoke.py` (Playwright) | **53s** | 41 |
| everything else | **34s** | 1251 passed, 24 skipped |
| **whole suite** | **~100s** | ~1337 |

**The benchmarks are not the bottleneck.** They are the smallest of the three blocks, and the
single slowest test in the repository is not a benchmark at all — it is
`test_desktop.py::test_both_shutdown_paths_warn_when_the_server_does_not_stop` at 10s, which
deliberately waits out two shutdown timeouts.

The premise behind U6 does not survive the measurement. That does not make U6 wrong as a *local*
development instruction — a 100-second wait between edits is still worth avoiding, and the user's
machine also runs their own server — but it removes the reason to build PR CI around excluding
the benchmarks. A 100-second suite is cheap in CI, where nobody is waiting at a prompt.

Consequence for the design: **PR CI runs the whole suite**, with no marker, no split and no
exclusion. Recorded as a decision (A13) rather than left implicit, because it reverses the
expectation the phase list was carrying.

The wall-clock figures are from this machine and will differ on a GitHub runner — likely slower,
as the shared runners are modest. The ratios are what matter here, not the absolutes.

## Version and tag mechanics — noted, not yet settled

Two details the release workflow has to pin down, found while surveying:

1. **`app/__init__.py` holds `__version__ = "0.1.0"` and no git tags exist.** So the release
   workflow needs a rule for the relationship between the tag and that string. The options are to
   derive the tag from the source (and fail the build if `v$(app.__version__)` does not match the
   pushed tag), or to let the tag be authoritative and stamp it into the artifact. The first keeps
   `app/__init__.py` as the single source it documents itself to be, and turns a mismatched tag
   into a failed build rather than a mislabelled download — that is the one to prefer unless there
   is a reason not to.
2. **The AppImage filename carries no version** — `build-appimage.sh:58` hardcodes
   `Home-Battery-Simulator-x86_64.AppImage`. Every release would attach an identically-named file.
   Since SmartScreen-style reputation and plain user confusion both attach to filenames, the
   release job should rename per tag. Worth doing in the workflow rather than editing the script,
   so a local build keeps its stable, predictable name.

## A gap CI could close, found while surveying: the committed CSS can drift

`app/static/app.css` (165KB) is **committed**, and generated from `app/static/src/app.tailwind.css`
by `npm run build:css`. `.gitignore:6` states the arrangement explicitly: Node is dev-time only,
the output is committed, and the app needs no Node at runtime.

Good for packaging — the PyInstaller bundle needs no Node, and PR CI needs no Node to run the
tests. But **nothing currently checks that the committed output matches its source.** A pull
request that edits `app.tailwind.css`, or adds a Tailwind class to a template, and does not
re-run `build:css` would pass every test and ship stale styles. The tests read the built CSS, so
they cannot see the difference.

This is squarely the class of thing PR CI is for: rebuild the CSS and fail if `git diff` is
non-empty. Cheap (one npm install, one command) and it makes the drift impossible rather than
merely unlikely.

**Not yet decided** — it is an addition to the user's request rather than part of it, so it is
offered rather than assumed. If it is not wanted, the drift stays possible and that is worth
knowing rather than leaving implicit.

## The finding that decides the Linux runner: a Python ABI constraint, not glibc

`packaging/build-appimage.sh:105-116` hard-fails when the frozen interpreter's minor version and
the system PyGObject's compiled `_gi` extension disagree:

> `FAIL: the frozen interpreter is $BUNDLE_PY_ABI but the system PyGObject is built for
> $GI_ABI_TAG. The compiled _gi extension would not import.`

The AppImage copies the **system** `python3-gi` out of `/usr/lib/python3/dist-packages/gi`,
including its compiled `_gi.cpython-3XX-*.so`, into a bundle whose interpreter `build-linux.sh`
pins to `--python 3.12`. The two must be the same minor version.

Verified on this machine — which is why the local build works at all:

```
/usr/bin/python3            → Python 3.12.3
.../dist-packages/gi/_gi.cpython-312-x86_64-linux-gnu.so
/etc/os-release             → 24.04, noble
```

**Ubuntu 22.04 ships Python 3.10**, so its `python3-gi` is `_gi.cpython-310` while the bundle is
3.12 — the gate fires and the build fails. **U12 is therefore not implementable as chosen**, and
for a reason that has nothing to do with the deprecation timeline found separately.

Three ways out, in rough order of cost, none yet chosen:

1. **Build on `ubuntu-24.04`** — matches the local, working configuration exactly. Costs the
   glibc floor U12 existed to lower: back to 2.39, so Debian 12 stays unsupported. A9 unresolved.
2. **Pin `build-linux.sh` to 3.10 for the 22.04 build** so the bundle matches that host's
   PyGObject. Keeps the 2.35 floor. Untested, and it changes the interpreter the artifact ships,
   which is a larger change than a runner label.
3. **Stop copying the system `gi`** and install PyGObject into the build venv instead, decoupling
   the bundle from the host's Python entirely. The cleanest fix and the largest — it rewrites the
   part of the AppImage build that phase 4 found most fragile.

Recommendation if a tie-break is wanted: **(1) now, (3) later** — take the working configuration
to get CI green, and treat the glibc floor as the separate piece of work it actually is, rather
than coupling it to standing up CI. That keeps A9 open and honest instead of appearing solved.

**Decided by the user, 2026-08-05: option (1), `ubuntu-24.04`.** Recorded as U14, superseding U12.
The consequence to keep visible: **A9 is not fixed by this CI work.** The released AppImage will
require glibc 2.39 and will not run on Debian 12 or older. That is now a deliberate, recorded
position rather than an artefact of where the build happened to run — but it is still a real limit
on who can use the Linux artifact, and option (3) remains the way out if it matters later.

## Verified: the committed CSS is stale on master today

The drift described above is not hypothetical. Measured by regenerating and diffing (then
reverting — nothing was committed):

```
npm run build:css
git diff --stat app/static/app.css
 app/static/app.css | 2 +-
```

A strict `build:css && git diff --exit-code` gate **would fail on master right now**. The
reported cause is a missing `-mt-2` utility, used at `app/templates/_panel_results.html:438`.

So adding the gate means first regenerating and committing the CSS. That is a real (cosmetic)
drift being surfaced, not a CI misconfiguration — which is the argument for the gate rather than
against it. Order matters: commit the regenerated CSS first, add the gate second, or the first PR
to touch CI fails for an unrelated reason.

**Resolved by the user the same day**, via a merge of `wt/uiux` (`d4b1b15`). Re-verified after the
merge: regenerating produces **no diff**, so the prerequisite is met and the freshness gate can be
blocking from the outset rather than phased in.

The gate is included as **blocking**. Note the user did not choose explicitly between the three
options offered — the answer was that the stale CSS had been fixed, which removes the obstacle to
the recommended option rather than selecting a different one. Cheap to drop if that reading is
wrong: it is one job in `test.yml`.

## The release jobs verify what they build (user decision)

Rather than build-and-upload, each release job runs the existing env-gated packaged suites against
its own fresh artifact before uploading:

- `BATTERY_SIM_APPIMAGE=<built>` → `tests/test_appimage.py` (structural + `--no-browser` run)
- `BATTERY_SIM_PACKAGED_BINARY=<built>` → `tests/test_packaged.py`
- either → `tests/test_packaged_ingest.py` (the websocket path, i.e. the `ws="auto"` defence)

These are the suites that would have caught the missing `libmanette` had they existed then, and
they need no display. The Docker isolation check (`verify-appimage-isolated.sh`) was offered
alongside and **not** chosen, so self-containment continues to rest on
`check-appdir-closure.py`, which runs inside the build — a static `DT_NEEDED` check that is
structurally blind to `dlopen`ed subsystems (see U10). Worth knowing that gap is not closed by
CI either.

## Other CI-relevant facts confirmed

- **No Node needed for tests.** The committed CSS is what the server serves; the suite never
  shells out to node. Node is needed only if the freshness gate is added.
- **Playwright:** `uv run playwright install chromium` — Chromium only (`test_smoke.py:94`), and
  headless by default, so no Xvfb.
- **Headless-safe throughout.** `test_desktop.py` fakes `webview` into `sys.modules` and opens no
  window; its one real-pywebview test only binds signatures via `inspect.signature`. No test needs
  a display, a D-Bus session, or outbound network — loopback only.
- **appimagetool needs FUSE.** `build-appimage.sh` invokes it with no workaround, while
  `verify-appimage-isolated.sh` already uses `APPIMAGE_EXTRACT_AND_RUN=1` for the product
  AppImage. Setting that env var at job level is the lighter touch than installing `libfuse2`, but
  whether it works for appimagetool itself is **unverified** — test both in a throwaway run.
- **appimagetool is fetched from the `continuous` tag** — an unpinned moving target. For
  reproducible CI, download a pinned release and pass `APPIMAGETOOL=`. It caches at
  `dist/appimagetool.AppImage`.
- **`verify-appimage-isolated.sh` could run in CI** — Docker is preinstalled on hosted Linux
  runners, it needs no privileged mode and runs its own Xvfb. Costs a few minutes and pulls
  `ubuntu:24.04` (Docker Hub rate limits apply). Its screenshot output is an artifact candidate.

## macOS and Windows: how much does not exist

`packaging/battery-sim.spec` is mostly platform-generic — `DATAS`, `HIDDENIMPORTS`, `EXCLUDES` and
the Analysis/PYZ/EXE/COLLECT pipeline all port. But every macOS/Windows-specific field is at an
inert default, and the spec's own header calls it "the Linux desktop build":

- **No `BUNDLE(...)` block** — so no `.app`, no bundle identifier, no `Info.plist`.
- **No `icon=`** — no `.icns`, no `.ico`. The only icon anywhere is the AppImage's
  runtime-generated placeholder PNG; `packaging/battery-sim.png` does not exist.
- `target_arch=None`, `codesign_identity=None`, `entitlements_file=None`.
- **`console=True`** — on Windows this opens a console window beside the app. The comment explains
  it is deliberate (the launcher prints its URL and fallback reason to stderr), so flipping it is
  a real trade-off, not a cleanup.
- `build-linux.sh` is bash with POSIX paths; there is no macOS or Windows build script.

So macOS/Windows is **"run the existing spec on that OS"** for a raw bundle, and **"does not exist
yet"** for everything that makes it shippable. This is what U11's `continue-on-error` is
absorbing, and it is worth being precise that those jobs will initially produce an unpolished
directory bundle rather than a double-clickable app.

The *application* is already three-platform aware — `app/config.py::user_data_dir()` handles
darwin/win32/linux and `test_desktop.py` pins all three by monkeypatching `sys.platform`. Only the
*packaging* is Linux-only.

## Corrections made during review

**`actions/download-artifact@v6` → `@v8`.** The implementer chose v6 by reasoning that it "pairs
with upload-artifact v7". Checked against each action's own `action.yml`: download-artifact's
current major is **v8**, and the two actions are versioned independently — they do not track
lockstep majors, so matching the numbers is not a rule that holds. Corrected, with a comment
saying why the mismatch is intentional so nobody "fixes" it back.

The same check confirmed all four `softprops/action-gh-release@v3` inputs used
(`draft`, `files`, `generate_release_notes`, `fail_on_unmatched_files`) exist and are spelled
correctly — those had been written from memory and flagged as unverified.

**`uv run pyinstaller` → `uv run --no-sync pyinstaller`.** The more interesting of the two, because
it would not have failed reliably. The three non-Linux jobs install PyInstaller with `uv pip
install` and deliberately keep it out of `pyproject.toml` (it is a build tool, not a dependency —
`build-linux.sh` gives the same reasoning). But a plain `uv run` **re-syncs against the lockfile
before running**, and the lockfile does not mention PyInstaller.

Reproduced locally against a copy of this project's `pyproject.toml` and `uv.lock`:

```
$ uv sync --no-dev && uv pip install pyinstaller && uv run pyinstaller --version
Uninstalled 1 package in 1ms
Installed 11 packages in 43ms
6.21.0
$ uv run -v pyinstaller --version
DEBUG Unnecessary package: pyinstaller==6.21.0
DEBUG Unnecessary package: pyinstaller-hooks-contrib==2026.6
```

PyInstaller **did** survive and the build ran — but uv classifies it as an "Unnecessary package",
i.e. a removal candidate, and surviving is uv's discretion rather than a guarantee. That is the
worst shape for a CI defect: it works until it doesn't, on a platform nobody can reproduce
locally, in the job that only ever runs at release time.

`uv run --no-sync` runs against the environment as installed and removes the question. The Linux
job's `uv run pytest` is **not** exposed to this — pytest is in the dev group and therefore in the
lockfile, so the re-sync installs it rather than evicting it. Checked rather than assumed.

Also verified rather than assumed:

- `package-lock.json` **is** committed, so `npm ci` will not fail at once.
- The version-extraction shell/Python in both the gate and the rename step **fails closed**:
  tested with a tree where `__version__` is absent, both exit 1 rather than emitting an empty
  version into a filename.
- `dist/Home-Battery-Simulator-x86_64.AppImage` and `dist/battery-sim/battery-sim` are exactly
  what `build-appimage.sh:55,58` produce, matching the env vars the verification step sets.

## What the adversarial review found

Reviewed by an agent that did not write the files, told to assume defects and go looking. Its
most useful contribution was **converging independently on the `uv run` problem** and supplying a
second mechanism the orchestrator's own testing had missed: `uv run` syncs **with the dev group by
default**, so `uv run pyinstaller` would have reinstalled pytest, playwright and httpx one step
after `uv sync --no-dev` deliberately excluded them. The bundle would still have been correct —
the spec's `EXCLUDES` names those packages — but only because the safety net was silently doing
the work. Both mechanisms are now in the comment.

The reviewer recommended `--no-dev`; **`--no-sync` was kept instead**, after testing both:
`--no-dev` fixes the dev-group half but still performs a sync, leaving the eviction risk live.
`--no-sync` answers both.

Acted on:

- **Job timeouts added** to all six jobs (5–45 min). There were none, so a wedged uvicorn
  subprocess — and several tests spawn them — could have sat on the 360-minute default.
- **Header job list corrected.** It named `macos-arm64` / `macos-x86_64` / `windows` as separate
  jobs; they are one `desktop-bundle` matrix.
- **Line-number reference replaced with a grep anchor.** The comment cited
  "build-appimage.sh lines ~105-119"; the check is at 108-120. Rather than correct a number that
  rots on the next edit, it now says to search for `GI_ABI_TAG` — verified to land on the check.
- **PyInstaller's unpinned-ness recorded** in the comment: it is not in `uv.lock`, so a release
  picks up whatever version is current that day. Pre-existing (`build-linux.sh` is the same), but
  it means the release build is not fully reproducible, and that should be said rather than
  assumed away.

Checked and **found correct**, so not changed:

- The Windows `Compress-Archive` nesting matches the POSIX `zip` branch — both produce
  `battery-sim/...`. The reviewer raised three possible defects here and withdrew all three.
- The `release` job's `if:` condition behaves as documented in all four traced cases (linux fails,
  a matrix leg fails, `workflow_dispatch`, `version-gate` fails).
- The verification step **fails loudly rather than skipping** if the build produced no artifact:
  the gates key on the env var being set, not on the path existing.
- Permissions are least-privilege; `find -printf` is GNU but the job is on ubuntu.

Two comment claims the reviewer flagged as unverified, both since **confirmed**: there are exactly
five `pytest.importorskip("websockets")` calls in `tests/test_packaged_ingest.py`, and
`tests/conftest.py:71` does use `setdefault`.
